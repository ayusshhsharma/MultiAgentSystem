# 🎓 University Faculty Live Demonstration Guide

This guide provides a structured walkthrough, failure contingency plans, and anticipated academic questions for demonstrating the **MultiAgentSystem** to university faculty.

---

## 📋 1. Pre-Demo Checklist

Complete these checks 15–30 minutes before entering the presentation room:

- [ ] **Laptop Power:** Battery charged to 100% and power adapter plugged in.
- [ ] **Diagnostic Preflight:** Open PowerShell and run:
  ```powershell
  python preflight.py
  ```
  Ensure it reports `READY for live demo`.
- [ ] **Network Connectivity:**
  - Verify campus Wi-Fi does not block `api.tavily.com` or `api.groq.com`.
  - Keep your **phone hotspot** active and paired as an instant backup network.
- [ ] **Offline Cache Verification:**
  - Ensure `demo_cache/` contains pre-generated JSON runs (run `python make_demo_cache.py` beforehand if empty).
- [ ] **Clean Presentation Workspace:**
  - Close background apps (Slack, Discord, heavy IDE instances, unnecessary browser tabs).
  - Open terminal and browser side-by-side at a readable font scaling (125% zoom recommended).
- [ ] **Launch Application:**
  ```powershell
  .\run_demo.ps1
  ```
  Keep one pre-generated run loaded in the browser session as an immediate fallback before starting.

## ⏱️ 2. 5-Minute Faculty Demo Script

### [0:00 – 0:30] Problem Statement (30 Seconds)
> *"Good morning professors. Standard Large Language Models struggle with academic and technical research for two fundamental reasons: static knowledge cutoffs and ungrounded hallucinations. Even when standard tools add web search, they often dump raw search snippets into a single prompt, producing superficial summaries with hallucinated or broken URL references. Our project, MultiAgentSystem, decomposes research into distinct, verifiable stages: structured web discovery, concurrent source extraction, cited report synthesis, and programmatic citation validation."*

### [0:30 – 1:30] Architecture Walkthrough (60 Seconds)
*(Point to the architecture diagram in the sidebar or presentation slide)*
> *"Rather than relying on a black-box prompt, our architecture separates responsibilities:
> 1. **Search Discovery:** Directly calls Tavily's search API, returning up to 5 authoritative sources and assigning persistent numeric IDs `[1]` through `[5]`.
> 2. **Concurrent Source Extraction:** A thread pool scrapes candidate HTML pages in parallel, stripping scripts, navigation, and boilerplate while retaining query-relevant snippets.
> 3. **Cited Report Writer:** An LCEL chain with strict prompting rules requiring inline citations for every factual claim.
> 4. **Deterministic Citation Engine:** A Python validation step checks every citation in the raw draft against real source IDs, removes hallucinated references, and programmatically compiles the Sources section.
> 5. **Critic Review:** An independent evaluation chain provides an objective quality audit."*

### [1:30 – 3:30] Live Execution on Prepared Topic (2 Minutes)
*(Submit topic: `Major reasons behind the recent fall in gold and silver prices in India` and click "🚀 Start Research")*

While the live progress widget updates, narrate the four stages:
- **Step 1 (Searching the web):**
  > *"Step 1 is calling Tavily to retrieve 5 verified, high-authority market and financial reports."*
- **Step 2 (Scraping sources in parallel):**
  > *"Step 2 uses Python's ThreadPoolExecutor to scrape the full article text from all 5 sites simultaneously. If any site is paywalled or blocks scraping, the pipeline falls back gracefully to Tavily's search snippet."*
- **Step 3 (Writer drafting report):**
  > *"Step 3 invokes our primary Groq model. We have a verification loop: if the model returns an empty or truncated report under 150 words, it automatically retries up to three times."*
- **Step 4 (Critic reviewing report):**
  > *"Step 4 runs our critic chain to evaluate factual depth and formatting."*

### [3:30 – 4:30] Results & Citation Verification (60 Seconds)
*(Switch between the 4 output tabs)*
> *"Notice three key elements in our results:
> 1. In **Tab 1 (Search Results)**, faculty can see the exact URLs and whether each page was scraped or fell back to a snippet.
> 2. In **Tab 3 (Final Report)**, notice that every factual claim in Key Findings is tagged with inline numbers like `[1]` and `[3]`.
> 3. Look at the bottom **Sources** section: this was **not generated by the LLM**. Our Python code extracts the cited numbers and builds the markdown links directly from verified search metadata. The LLM can never hallucinate a link because it does not write the Sources section."*

### [4:30 – 5:00] Limitations & Future Work (30 Seconds)
> *"To be transparent about limitations: this is currently a linear pipeline without an automated revision loop. Our planned next step is migrating this to a formal LangGraph cyclic StateGraph, where the Critic's score dynamically routes poor drafts back to the Writer for iterative refinement. We also have an empirical evaluation harness measuring faithfulness across 18 topics, currently in progress."*

## 🚨 3. "If Something Fails" Contingency Table

| Failure Mode | Cause | Immediate Demo Action |
| :--- | :--- | :--- |
| **Campus Wi-Fi blocks Tavily or Groq** | Institutional firewall or captive portal | 1. Switch laptop connection to phone hotspot.<br>2. Or immediately open sidebar → **Saved Demo Runs** → Click **Load Saved Run**. |
| **HTTP 429 / Rate Limit Exceeded** | Groq free/developer tier tokens-per-minute ceiling | Say: *"We hit the free-tier API rate limit. Fortunately, the system auto-saves every run."*<br>Select a saved topic from the sidebar and click **Load Saved Run**. |
| **Blank or Truncated Report** | Transient LLM generation timeout | The pipeline automatically retries 3 times. If all 3 fail, load the saved run from the sidebar. |
| **All Web Scraping Times Out** | Target websites actively blocking scrapers | The pipeline automatically falls back to search snippets (`⚠️ snippet`) so the report generation continues uninterrupted. |

## ❓ 4. Anticipated Faculty Questions & Model Answers

### Q1: Why use a multi-step / multi-agent design instead of a single prompt with web search?
> **Answer:** *"A single prompt creates a black box where retrieval, filtering, drafting, and citation happen in one forward pass. If the output contains an error, it is impossible to diagnose whether search, extraction, or synthesis failed. Multi-step decomposition makes each stage auditable: we inspect raw search results, verify scraped text, validate citations deterministically in Python code, and evaluate with a separate critic."*

### Q2: How do you prevent citation hallucination?
> **Answer:** *"We use a two-tier defense. First, prompt engineering forces the model to use only provided numeric IDs (`[1]`, `[2]`). Second, our code post-processes the draft with regex: if the model invents a citation like `[9]` when only 5 sources exist, `finalize_citations()` deletes it. Furthermore, the final `## Sources` section is generated purely in Python from verified metadata—the LLM is forbidden from writing URLs."*

### Q3: What happens when target websites block web scraping?
> **Answer:** *"In `tools.py`, our `scrape_one()` function treats HTTP errors, 403s, and timeouts as clean failures and returns an empty string. `scrape_many()` detects this and falls back to Tavily's high-relevance search snippet (up to 1,500 characters). This ensures the writer always has grounded context even if all 5 websites block automated scraping."*

### Q4: How do you prevent hallucinations in the generated text?
> **Answer:** *"We ground the model strictly on numbered source text delimited by `<content>` tags. We enforce temperature 0.3 for factual consistency. Additionally, our evaluation harness (`evaluate.py`) implements LLM-as-a-judge faithfulness checks, verifying sentence-by-sentence whether claims are directly supported by the source text."*

### Q5: Why doesn't the Critic agent's feedback automatically trigger a rewrite?
> **Answer:** *"In this initial implementation, the Critic operates as an observational audit layer to keep latency and token usage within presentation constraints. In our future roadmap, we are refactoring the pipeline into a LangGraph `StateGraph` with conditional edges, so that reports scoring below 7/10 automatically loop back to the Writer with critic feedback."*

### Q6: What is your empirical evaluation methodology?
> **Answer:** *"We built an automated evaluation script (`evaluate.py`) testing 18 diverse technical, financial, and scientific topics against a single-prompt baseline without search. It benchmarks latency, word count, scrape success rates, citation coverage, hallucination rate, and semantic faithfulness via a secondary judge model (`qwen/qwen3.8-27b`)."*

### Q7: What are the main technical limitations of your system?
> **Answer:** *"First, token limits on Groq require us to truncate scraped page content to 2,000 characters. Second, the scraper uses synchronous requests in a thread pool rather than an asynchronous browser engine, so JavaScript-heavy Single Page Applications cannot be fully rendered. Third, the pipeline is single-pass rather than cyclic."*

### Q8: If you had another semester to work on this, what would you improve?
> **Answer:** *"Three things: First, implementing a cyclic LangGraph loop for iterative refinement. Second, adding Playwright for headless browser scraping of JavaScript SPAs. Third, adding multi-provider fallbacks to Google Gemini or local Ollama instances when cloud rate limits are reached."*
